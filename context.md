## Decisions

Decisions made after the brief. Format: date, decision, reason.

### 2026-10-30 — "Try it" (phase 1, step 3l)

- **The same code as a run, with the text swapped.** A try doesn't imitate a run: `Prompts::resolve()` takes an unsaved draft revision in place of the current one, and the planner, copywriter, reviewer and change planner each had their model conversation split from their saving (`Planner::think()`, `CopyWriter::compose()`, `Reviewer::judge()`, `Changes::instruct()` and `compose()`), so a try goes through exactly the prompt, tools, limits and scoring a run would. What a try shows is therefore what a run would do with that text, which is the point of trying.
- **One sample per prompt type, the brand's own where it has one.** The planner and copy prompts run on a sample brief (the brand's latest request's brief, else a stock whey sale), with the real store to search and the first placement of each shape; the images and changes prompts on a sample scene (the latest plan's image prompt, else a stock one) and a sample change; the review prompts on the brand's latest clean image or finished ad whose file is still there, so the new criteria can be read against the score the saved review gave. Review prompts can't be tried before the first run; the page says so.
- **An images try makes a real picture, small.** The images prompt is only rules appended to a scene, so the only honest try is to generate: one square image at the smallest size the brand's image model makes, kept a day under `prompts/tries/<brand>/` and removed by the nightly clean-up. Everything else is a text-model call.
- **A daily test budget per person, as spend.** `prompts.try_daily` (default $2, platform-wide; 0 switches "Try it" off) is checked before a try starts, against the day's `spend` rows of kind `try` for that person; a try is also refused when their monthly budget or the company's is used up, and its cost counts toward both. Spend shows tries under Kinds of work as "Prompt tries".
- **Queued, not in the web request.** A try is a job (`TryPrompt`) with its result in the cache for an hour under a random token the page holds, polled every three seconds while running: an image can take a minute and a planner a few searches, longer than a web request should wait. Nothing about a try is saved in the database: not the text, not the result.
- **Not yet:** choosing which output a review try scores (it's the latest); trying additions; keeping a history of tries.


### 2026-10-30 — Cut-outs (phase 1, step 3k)

- **Photoroom, as a plugin like the others.** `BackgroundRemover` is a capability interface beside the store, image and language ones; `plugins/photoroom` is its first plugin (the Basic plan's `POST /v1/segment`, a photo in, a PNG with transparency out, cropped to the product). remove.bg was the other candidate, but its self-service API closes on 1 December 2026, and Higgsfield's remover is only on its website product. A second remover would be another plugin and a choice under Settings → Store.
- **Only the photos an ad would use, once each.** A cut-out is made for each current variant's own photo, or the product's first photo when the variant has none (`Cutouts::wanted()`), never every photo on the store. It's kept beside the photo (`product_images.cutout_path`, on the files disk under `catalogue/<brand>/cutouts/`) until the store gives the photo a new address, when the catalogue already forgot it. The store read queues the cut-outs due when it finishes, so new products are ready by morning; "Make the cut-outs" on Products does the rest by hand, including trying failed ones again.
- **The kit's pack shot wins, the cut-out is the fallback.** The composer and the reviewer take a transparent pack shot uploaded to the brand kit for the variant first, then the cut-out, then nothing (the ad says why in its checks). A cut-out that comes back without see-through edges is refused and the reason kept on the photo, so a bad result never ends up on an ad.
- **Price as a setting, since Photoroom doesn't say.** Photoroom charges per image on a prepaid plan and reports no cost per call, so `photoroom.price_per_image` (default $0.02) is what each cut-out is recorded as (`spend` kind `cutout`), and Spend shows it under Kinds of work. "Check now" tries the cut-out call with no photo attached: a refused key fails before the missing photo does, and nothing is charged.
- **A failure is written on the photo, not retried for ever.** `product_images.cutout_error` holds the last reason; a photo that failed is left out of the nightly batch and tried again only from the page, so a photo the service can't cut doesn't cost an image every night. The job itself tries three times when the trouble is temporary (the service busy, the store's CDN down).

### 2026-10-29 — Spend and budgets (phase 1, step 3j)

- **One Spend page for admins, from the spend rows.** Every provider call is already a `spend` row (brand, person, request, provider, kind, amount); the page adds them up rather than keeping separate totals, so it's always right and costs nothing to maintain. Admins only (`budgets.manage`): a person sees their own budget line on each request, which is what they need. Totals are tables with each row's share; no charts until someone asks.
- **Estimates checked against actuals.** The page lists the period's confirmed requests with the estimate and the actual cost, the dearest first, and marks a request whose actual is more than $0.50 over its estimate: that's where the model prices or `budgets.text_allowance` want a look.
- **Per-person budgets live on Users.** Beside each person's spend this month against their budget ("$12.50 of $200.00, the default"), an admin presses Change and types a monthly amount, or puts them back on the default. The brief's "per-user monthly budget, set by Admins".
- **The warning line tells admins once a month.** When a spend row takes the company past `budgets.alert_percent` of `budgets.company_monthly` (counting the estimates of runs still going), the platform admins get a notice under the bell and an email (`BudgetAlert`), once per month: the check is cheap (two sums) and runs on every spend row, with the activity log's `budget_alert` entry as the once-a-month marker, so a cleared cache can't repeat it. Admin alerts don't go through a person's "Email about" choice, like the scheduler alert.
- **Not yet:** a daily digest; budgets per brand (the brief has company and person); exporting the tables.

### 2026-10-29 — Retention (phase 1, step 3i)

- **The files go, the record stays.** The nightly clean-up deletes a rejected output's image and thumbnail from the disk and stamps `removed_at`; the row keeps its score, reason and review, so the request page still says what was made and why it was rejected (with "File deleted after a day" where the picture was), and the prompt-tuning flow still has the history. Shortlisted outputs are kept until their request is deleted (no request deletion yet).
- **A day by default, per brand.** `retention.rejects_days` (default 1, 1–90; platform and brand) under Review and quality, counted from when the output was judged. The task runs daily at 4 AM in the platform's time zone, from the scheduler, and can be run now from Scheduled tasks.
- **An original with a living version is kept.** Changes are made from the original image, so a rejected original isn't removed while any changed version made from it still has its file; once the versions are gone too, it follows (the clean-up runs in passes). Nothing can be changed or run from a removed image, and the page says so.

### 2026-10-29 — Notifications (phase 1, step 3h)

- **A notice goes to the person the event is about, never to everyone.** The request's owner is told when the planner stops for them (a question, the plan ready to confirm, or planning failed), and when the run finishes or fails; whoever asked for a change or a shape run again is told when it lands, with the score and whether it joined the shortlist. Admin alerts (the scheduler stalled) stay as they were. Three groups a person can choose from, so the choice stays plain: "a request needs me", "a run has finished, or failed", "a change I asked for has finished".
- **Always in the app, email by choice.** Every event is a row in `notifications` (Laravel's database channel) shown under the bell, with the count unread; the email is a second channel, sent only for the groups ticked under Your account → Notices (`notify.email`, a user-scoped setting whose platform value is the starting choice for everyone: "needs me" and "finished" on, changes off, since the person is usually watching the page). The email goes through the Gmail transport already connected for invitations.
- **No email for what was already seen.** The email is queued with a delay (`notify.email_delay`, default 2 minutes, advanced) and dropped if the notice was read meanwhile. Opening the request page marks its notices read, so someone watching the planner answer isn't emailed about the question they just answered; the bell marks one read when it's opened, or all at once.
- **Not yet:** a daily digest; notices for budgets running low (they come with the spend page); notices to a brand's admins about other people's requests (nobody asked for them).

### 2026-10-29 — Iteration (phase 1, step 3g)

- **A change is a generation, not a new request.** "Make a change" on a clean image makes a `generations` row with `source_output_id` (the image it was asked on), `user_id` (who asked), `instruction` (the words typed) and `count` 1, run in its own batch; the request stays `done` while the page polls until the change lands. "Run again" on a shape is a generation with `user_id` and no source: the target's count again, the prompt made from the plan and the Images prompt as they are now (so a prompt edit can be tried on a finished request). Both are checked against the budgets first (the model's price per image times the count, plus `budgets.text_allowance`), need `update` on the request, and record their spend like the run (the planning call as kind `change`).
- **Always from the original, folded.** Before generating, `Changes::plan()` asks the text model (the new **Changes** prompt type, `PromptType::Change`, with `{brand}` and `{brand_kit}`) to turn the new change plus every change already asked in the chain into one instruction, and to sort it: `edit` (local: the original image goes with the instruction as a reference, "keep everything not mentioned exactly as it is") or `regenerate` (global, or a model without `edits`: the whole prompt written again). What to keep (subject, composition, palette, light) is written after the instruction, then the brand's Images rules. `iterate.max_depth` (default 1, advanced) is how many steps from the original a change may be made: 1 means always from the original; the folded instructions are stored on the generation (`change` JSON: mode, source, instruction, keep, folded, the Changes revision ids).
- **No masks or seeds yet.** Neither contract exists on the image providers here; a local fix goes to the model as an edit with the original image and the instruction, which is what Gemini and OpenAI edits take. Masks and seed-keeping come with a provider that offers them.
- **Versions beside the original, nothing replaced.** The new image has `source_id` (the image it was asked on) and is shown under it with its score and the original's ("76 down from 84" in amber when lower). `Shortlist::judge()` applies the run's rules to the one output (checks, review, hard fails, the minimum) without re-ranking the others, so an original already shortlisted stays shortlisted and a passing version joins it. Finished ads are composed again from the version by the composer, so the product and the words can't drift, and are judged the same way.
- **A limit, then a fresh request.** `iterate.max_changes` (default 3) counts every version in an image's chain; after that "Make a change" is replaced by "Start a fresh request", which opens the new-request form with the same choices and the brief with the changes written in ("Changes wanted from the last run: …"). A change still being made blocks another on the same image.
- **Not yet:** the "describe the problem" prompt-change flow doesn't read repeated instructions across people (it needs more runs to be useful). A change landing is told through notifications (step 3h).

### 2026-10-29 — Prompts with revisions (phase 1, step 3f)

- **Five prompt types, rows per brand, no git.** `prompts` (brand, type, user for additions, current revision) and `prompt_revisions` (number, body, settings, note, method starter/hand/ai/rollback, the request that produced an AI draft, restored_from, author, time). A brand's prompt is made from `App\Prompts\Starters` as revision 1 the first time it's needed; the starters are the texts the planner, copywriter and reviewer used until now, so nothing changes until someone edits. Video prompts come with video (phase 3).
- **Placeholders, not baked text.** The brand kit isn't copied into the prompt; the text holds `{brand}`, `{brand_kit}`, `{asking}` (planner), `{language}` (copy), `{criteria}` and `{hard_fails}` (review), filled by `Prompts::resolve()` at run time, so a kit edit reaches every prompt at once and a prompt edit never goes stale. The editor says what each placeholder becomes and warns, without refusing, when one is removed.
- **Criteria and weights are rows, not prose.** The review prompts keep their criteria (name, weight, what to look for) and hard fails as structured settings on the revision, so the app can still compute the weighted overall and the `submit_review` tool still lists the keys. A row keeps its key when its name is edited or when the AI sends it back (reviews are stored by key); a new row gets one from its name. The diff shows them as lines after the text.
- **"Describe the problem" drafts, people save.** `PromptAssistant` gives the text model (`llm.default_model`) the current prompt, its placeholders to keep and the problem in plain words, and asks for the whole changed prompt with a two-sentence explanation through a `propose_prompt` tool. The page shows the explanation and a side-by-side diff; Accept saves it as a revision of method `ai` with the problem recorded, Adjust loads it into the editor (the save is still `ai` with the problem), Discard drops it. Nothing is saved by the assistant itself. Spend kind `prompt`, against the brand and the person.
- **The image prompt type is the standing rules.** The planner still writes the scene per request; the brand's "Images" prompt is appended to every shape's prompt after the plan's scene and the shape note (starter: the no-text rule that `Runs::NO_TEXT` was), with the person's additions after that.
- **Additions are per person per type per brand**, appended as "Additions from {name}:" after the brand's prompt whenever that person runs, saved as revisions of their own prompt row (`prompts.personal`: Admins and Creators); admins see everyone's on the page. Which revisions a piece of work used is on `requests` (planner), `generations` (images), `copies` and `reviews` as `prompt_revision_id` and `addition_revision_id`, and the request page lists them ("Planner v2; Images v1 + Ada's additions v1; …").
- **Rollback is a new revision** pointing at the one restored, so the history never loses a step. Saving an unchanged text is refused ("Nothing changed.").
- **"Try it"** (run an edited prompt on a sample brief without saving, on a small test budget) was built in step 3l (2026-10-30), below.

### 2026-10-29 — Review and the shortlist (phase 1, step 3e)

- **The model scores, the app decides.** `Reviewer` sends the review model (`llm.review_model`) the picture as a JPEG scaled to `review.image_px` (1024), the brief, the plan, the image prompt and, for ads, the placement and what the checks found, plus the real pack shot from the kit so the label can be compared. The model scores each criterion 0–100 with a `submit_review` tool and names hard fails; the app computes the weighted overall (`Reviewer::score()`), never the model. Criteria and weights live in `ReviewPrompt` until the prompt editor: clean images are scored on the brief (30), brand look (25), technical (25) and working on a phone (20); finished ads on the brief (25), brand look (20), product accuracy (20), text (20) and technical (15). Hard fails: altered label, wrong words, distorted people, off-brand.
- **Checks reject before review.** An ad that failed a size, file-size or safe-zone check is rejected on that alone and never sent to the reviewer (no cost, no second opinion on a certain fail). A missing pack shot isn't a check failure; the reviewer sees the note.
- **The shortlist is made once, when the run finishes.** `Shortlist::make()` groups clean images by shape and ads by placement and language, drops anything with a hard fail, a failed check, a failed review or a score under `review.min_score` (70), and shortlists the best `review.deliver` (3; the request's own "Deliver the best" overrides) by score. Everything else is rejected with a reason in words ("Scored 60, under the minimum of 70", "the best 3 were chosen", "Not reviewed: …"). Rejects stay visible under a fold "kept for a day in case the reviewer was wrong" (the nightly deletion comes with retention).
- **Review is a job per output in the run's batch**, so a run is done only when its reviews are. A review that fails leaves the output out of the shortlist with the reason, never stops the run.

### 2026-10-29 — Copy (phase 1, step 3d)

- **Copy is a job per placement and language, in the run's batch.** `WriteCopy` calls the text model once per placement that takes copy (its limits from the platform library, filtered by the request's choice: captions, ad copy or all) in each language the request asked for, with a `submit_copy` tool whose schema lists exactly the pieces and limits. `copy.versions` (default 3) different takes per call.
- **Limits are counted by the app, not trusted.** Characters (spaces count) or, for hashtags, the number of tags; a tag without # gets one. Anything over goes back to the writer as a tool error naming the version, the piece, the count and the limit, up to `copy.rewrites` times (default 2); after that the version is shown with its count in red rather than hidden. Every version shows "n/limit" per piece with a Copy button.
- **The words on finished ads are copy too.** For each language other than English, one `WriteCopy` writes the ad's headline (40), sub-line (80) and call to action (20) in that language; the composer uses them for that language's ads. English ads use the plan's words. An image landing before the French words exist is composed in English at once and in French when the words land (the copy job adds those compose jobs); an image landing after is composed in both. Ad files are named with the language ("…-feed-45-fr-1.png").
- **The prompt** is the brand kit's voice (words to use and avoid, calls to action, legal lines), the plan (summary, offer, audience, CTA, product) and the placement with its platform note, in the language asked for ("as a native speaker of marketing would, not as a translation"); no claims filter, as decided. Built in code (`CopyPrompt`) until the prompt editor arrives.

### 2026-10-29 — The composer (phase 1, step 3c)

- **A layout is a handful of plain choices, not a design tool.** `layout_templates` per brand and shape: headline position and alignment, text size and colour, whether to darken the picture behind the words, logo corner and size, product side and size, the call to action as a button or text, and toggles for the offer details, the legal line and a price badge. `AdHtml` turns those into pixel boxes for any placement size, inside its safe zone plus a 5% margin, so a changed spec in the platform library moves the words without touching the layout. The built-in layout per shape (words on top and the product below on a story; words beside the product on a feed or a banner) is used until the brand sets its own; "Add the starting layouts" seeds them for editing, and Preview renders the layout on a plain backdrop with the brand kit.
- **Chrome renders, GD converts, code checks.** Headless Chrome screenshots the page at the exact pixel size (`composer.chrome_path`, `composer.timeout_seconds`); the PNG becomes JPEG at falling quality when the placement doesn't take PNG or the file is over its limit (WebP when that's what it takes). Four checks are recorded on every ad: exact size, file size under the placement's limit, every placed box inside the safe zone, and whether the pack shot was placed. A failed check is shown on the ad, not hidden; the review step will weigh it.
- **The product is the kit's transparent pack shot for the variant, or nothing.** The store's photos have backgrounds, so until background removal exists an ad without a transparent pack shot in the kit leaves the product off and says so in its checks. Pack shots, text, logo and price never go through the image model.
- **Ads are made as the images land, in the same batch.** `GenerateImage` adds a `ComposeAds` job for its image to the running batch (requests for finished ads or both), so "done" means the ads are done too. A composer failure is written on the shape (`generations.compose_error`) and the clean images stay.
- **One language for now.** Ads are composed in the request's first language with the plan's English headline; the copy step will write the headline and offer per language and compose the French side.

### 2026-10-29 — Generation per shape (phase 1, step 3b)

- **One job per image, in a batch per run.** A run is a Laravel job batch (`job_batches`, `requests.batch_id`) of `GenerateImage` jobs on the default queue, one per image, so a six-worker Horizon makes six images at once, each job stays well inside the queue's timeout (one provider call, `images.timeout_seconds`), and a failure or refusal of one image never costs the others. The batch's `finally` marks the request done (any image came back) or failed (none did) with the actual cost. "Stop the run" cancels the batch: queued jobs are dropped, an image already made is kept.
- **Busy providers are tried again, refusals aren't, bad keys stop the shape.** `generation.retries` (default 2) more attempts after a rate limit or outage, with a short pause; a refused picture (`ImageException::$blocked`) counts as one failed image with the provider's reason on the shape; a reason that would fail every image (no connection, a refused key, an unknown model) fails the whole shape at once so the run doesn't burn through every job to learn it.
- **The prompt per shape** is the plan's scene, the plan's note for that shape, and a fixed no-text line (`Runs::NO_TEXT`: the composer sets the words). Style references uploaded with the request go with the prompt where the model takes references, up to its limit; product shots don't (they're for the composer). The prompt as sent is kept on the generation.
- **Outputs live under the request** on the app's disk (`requests/{id}/outputs/{generation}/{n}.png` with a 480-px WebP thumbnail), served through the app to people who may see the request, downloaded as "title-4x5-3.png". Spend rows per image carry the model's provider; `requests.actual_cost` is the run's total including planning.

### 2026-10-29 — The request flow (phase 1, step 3a)

- **The planner is a tool loop, not a form.** `App\Requests\Planner` gives the planning model three tools: `search_products` (the catalogue search, run in code), `ask_questions` (at most `requests.max_questions` a round, `requests.max_rounds` rounds, then the tool is withdrawn and the prompt says to decide with assumptions) and `submit_plan`. Product and variant questions carry the store's own options with pictures; "Any" is always offered for a size or flavour. Answers go back as plain text in the next planning message (stateless re-plan), and a chosen variant is pinned on the request so it isn't looked up again.
- **The plan is the planner's; the targets and the money are the app's.** The model returns the brief made clear (summary, offer, audience, CTA, product, image prompt, per-shape notes, model and why). Code then makes one `request_targets` row per placement, grouped by shape, with the count (`generation.per_ratio`, or the request's own) and the estimate from the model row's price table at the brand's size (`images.default_size`) and the provider's default quality (`ImageProvider::defaultQuality()`, so OpenAI's estimate uses `openai.quality`). The person's choices win over the planner's: model, count, product.
- **Image prompts describe the scene, never the product or the words.** The system prompt says so: the real pack shot is composited and the composer sets the words, so the prompt leaves space and never describes the label. The prompt used is built from `BrandKits::summary()` until the prompt editor exists; its text isn't yet stored per request (the revisions step will).
- **Budgets block starts, not runs.** `App\Budgets\Budgets`: company and per-person monthly limits as settings (`budgets.company_monthly`, `budgets.user_monthly`, a `user_budgets` row overrides a person's), spend as rows in `spend` (every provider call, priced from usage) plus the estimates of confirmed runs still going, in the platform's time-zone month. "Confirm and run" is refused when the estimate exceeds what's left for the person or the company, with the figures. Estimates add `budgets.text_allowance` for the text model's copy and review, which can't be priced before the run.
- **Public or private per request**, switchable at any time by its creator or an admin; `RequestPolicy` (view: creator, public, or `requests.view_all`; update: creator with `requests.create`, or `requests.view_all`). The Requests list is the brand's first sidebar item and where sign-in lands.
- **Reference images on a request** are stored on the app's disk under `requests/{id}/references` and served through the app to people who may see the request; each is Style or Product, as decided earlier.

### 2026-10-28 — The platform library (phase 1, step 2c)

- **Rows, not code.** `platforms` and `placements` tables, edited on Platform → Platforms (Admins, `platforms.manage`). A placement records pixel size, the aspect ratio it's generated at, a safe zone as pixels from each edge, whether it takes images, video or both, file types and largest sizes for each, the video length range, and copy limits per piece (primary text, headline, description, caption, hashtags: `App\Platforms\CopyField`), plus notes and a per-platform note for the prompts ("TikTok: native, unpolished feel").

### 2026-10-28 — Second round with Lesley

**Iterating without degrading.** Lesley: in practice, repeated edits make results worse and worse. Built in:
- Edits branch from the root, never from the previous edit. "Make a change" takes the original clean generation (full resolution, stored as PNG) as the source, and the planner folds every change asked so far into one instruction, so the fifth change is still one hop from the original. Setting `iterate.max_depth`, default 1.
- The planner sorts each instruction: a local fix (remove the object, fix the hand) goes to the model's edit or inpaint call with a mask where the model supports one; anything global (darker, different setting, different mood) regenerates from the amended prompt, keeping the seed where the provider allows it, instead of pushing the whole frame through image-to-image.
- Pack shots, text, logo, price and CTA never go through the model: the composer puts them back after every iteration, so the product and the words can't drift.
- Every iteration is reviewed with the same rubric and shown beside its parent with both scores; a drop is flagged. The parent is never replaced, and any version can be shortlisted.
- The edit carries "keep" constraints derived from the brief and the original prompt (subject, composition, palette), so the model doesn't redraw what wasn't asked for.
- Setting `iterate.max_changes` (default 3) per output: after that the app suggests a fresh run with the changes folded into the brief. Repeated instructions across users ("less pink") feed the "describe the problem" prompt-change flow.

**Hosting.** Same Plesk server as the CS app. Needs headless Chrome (composer) and ffmpeg (video) installed there, its own Horizon service and database, and video assembly on a single low-priority worker so it never starves the CS app.

**Notifications.** Email from Lesley's address through the Gmail API transport (lifted from the CS app); Lesley's account is the app's main account. In-app notices too. Which events email is a setting per user.

**Retention.** Rejected outputs are deleted nightly (`retention.rejects_days`, default 1). Shortlisted outputs stay until their request is deleted.

**Reference images on the request screen** are optional, not required. When one is uploaded the user says what it is: Style (look and mood for the planner's image prompt) or Product (a pack shot to use instead of, or beside, Shopify's). Default Style, since products come from Shopify.

### 2026-10-28 — Brief review with Lesley

**Relationship to the CS app**
- 100% standalone: own codebase and database, no shared modules, no shared tokens. Claude had suggested shared modules; Lesley doesn't want that.
- Code is lifted from the CS app and modified here, so the app works the same general way: settings registry with per-brand values, connections per brand with encrypted secrets, navigation, permissions and providers registered from service providers, Google sign-in limited to company domains, activity log. The CS app itself is never changed.

**Products: real pack shots, composited (reverses the brief's phase order)**
- The brief had reference-image generation as the main path and compositing as a phase 2 fallback. The Canadian Protein `marketing-images` skill learned the opposite: the label is where AI product imagery fails most visibly, and every approved creative uses real pack shots. So phase 1 composites real pack shots into generated scenes; generated-with-reference moves to phase 2 as an experiment, with the label check.
- **Background removal** is in phase 1: Shopify pack shots have a baked white background. Cutouts are made once per variant image and cached (service to choose; Higgsfield has a background remover).
- **Packaging dimensions per variant.** Sizes differ a lot within a product (2 kg, 1 kg, 1 lb), so when two products or sizes share a frame each is scaled by its real dimensions. Dimensions are entered per variant in the app (Shopify holds weight, not size). A variant without dimensions can't be composited beside another; alone it's fine.

**Bilingual from the start**
- English and French throughout, although nothing is marketed in French today. Copy and finished ads are produced per language chosen on the request; brand kit voice, CTAs and legal lines, layout templates' text and the prompts take both languages (the CS app's `Translated` setting control). A French run is never automatic; the request chooses its languages.

**Iterating on a result** (added; the brief had the `edit` call but no flow)
- Any output gets "Make a change" (an instruction such as "darker background", sent as an edit with the output as the source) and "Run again". The result is a new output linked to its parent, reviewed and counted against budgets like any other. A target can also be re-run with the plan unchanged.

**Generate per aspect ratio, compose per placement**
- One generation per aspect ratio in the run (a 1:1 image serves Instagram feed, Facebook feed, LinkedIn and X). The composer then produces each placement at its exact size with its own safe zone and copy limits. Cuts generation spend by three to four times.

**Budgets**
- All AI spend counts: image and video generation, and the language model's planning, copy and review calls.
- A run that was allowed to start always finishes, even if actuals pass the budget. Budgets block the start of new runs; they're a protection, not a hard cut mid-run.

**Prompts and people**
- Admins see every generation (public or private) and change the brand prompts.
- Each user can keep personal additions to each prompt type for a brand, appended after the brand's main prompt when that user runs. Admins can read them. Every generation records the brand prompt revisions and the user's addition it used, so a result can be traced.

**Viability points agreed**
- Deterministic checks are code, not AI review: pixel size, file size, copy character limits, safe zones on composed ads. Composed text is exact by construction. AI review keeps judgment: brief fit, brand look, product accuracy on generated references, technical defects, platform feel.
- Reviewers are given the brief and the output (and the Shopify image for product checks), never the generation prompt.
- A second reviewer model is a plugin setting (off by default); Gemini is needed for video anyway.
- Actual cost comes from provider usage (tokens, credits) priced by the app's price tables, reconciled against invoices monthly; per-call billing data isn't generally available.
- Data model: per-user budgets live on one table (`budgets`), not also on `users`. The `providers` table in the brief is a connections table (a plugin is code; a row is a connected account with its encrypted key), named `connections` as in the CS app.
- The request screen's "number of variants" is the run's "generate per aspect ratio" shortlist setting, not a separate field.
- Humans approve before anything leaves the app: download only, as the brief says.
- Higgsfield: its API runs on a separate prepaid balance (confirmed). Trademarks in a prompt are rejected (`ip_detected`), so the planner strips brand names from image prompts. Whether its enhancer is reachable through the API is an open question above.
